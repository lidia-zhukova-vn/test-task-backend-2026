# Тестовое задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.

## Результаты реализации

## Что дорого
1. db.session.commit() внутри цикла для каждой сущности - ~70000 транзакций
2. фильтр AbstractCustomer.amo_customers.op('@>')(...) - ~70000 GIN-запросов для поиска существующего пользователя
3. полное обновление JSONB (update_jsonb_field) - ~70000 UPDATE
4. select(AbstractCustomer) + filter_abc_customer - 1 полное чтение таблицы + до 4 UPDATE и commit на строку
Итого: до 70000*7 = 490000 запросов 
### Что изменено
#### Схема хранения
AbstractCustomer с jsonb был заменён на две отдельные реляционные таблицы.
Это дало возможносто сделать быстрее поиск по идентификаторам и логинам, в том числе при помощи индексации
1. Customer - таблица пользователей
  - amo_id - первичный ключ, NULL для «сирот»
  - merged_amo_ids - JSONB, для поглощённых amo_id при мердже
  - login - проиндексирован
  - name - проиндексирован
  - api_value, contacts, companies - jsonb, сырой ответ
2. Lead - таблица сделок
   - amo_id 
   - customer_id - проиндексирован
   - login - проиндексирован
   - name
   - api_value, contacts - jsonb, сырой ответ
#### Изменения в программе
Относительно изначального варианта, были дореализованы бизнес-логики: например, в оригинальном коде не искалось "удалить"
Весь процесс collect_leads_customers () разделён на 4 фазы:
1. preload() - единоразовое чтение индексов пользователей и сделок 2 SELECT-ами
2. customers_action() - проходит по всем покупателям из AmoCRM и создаёт/обновить соответствующую строку Customer.
Эффективно за счёт добавления новых пользователей батчами и flush после
3. leads_action() - проходит по всем сделкам и привязывает каждую к покупателю по amo_id или логину, иначе сделка объявляется "сиротой"
4. merges_action() - вливает victim покупателей в target покупателей по причине "сделка уже была привязана к target, но по логину указывает на victim"
### Почему теперь дешёво
1. db.session.commit() только в конце 2, 3 и 4 фаз - 3 коммита
2. в preload() - 2 запроса (получение id из таблиц)
3. в customers_action() - до 20000 запросов (добавление уникальных пользователей)
4. в leads_action() - до 50000 запросов добавления пользователя для orphan сделки (что маловероятно, 
настолько много будет подобных случаев, будем считать, что их будет около 30000), до 50000 добавления новых сделок
5. в merges_action() - до 50000 удаления "совпадений" (опять же, их явно будет меньше, предположим, что до 30000)

Итого:
В среднем случае - ~130000 (20k+30k+50k+30k) запросов и 3 коммита 
В худшем - ~170000 (20k+50k+50k+50k) запросов и 3 коммита, что всё ещё почти в 3 раза меньше исходного варианта

### Что оставлено
1. Код amocrm.py
2. Функции в abstract_customer.py - на всякий случай, если другие модули их используют, а не только данный main.py;
минимально изменены, чтобы быть корректными относительно новой модели
3. JSONB поля в таблицах - разделены на две таблицы, но оставлены как сырой ответ, чтобы в случае чего меньше пришлось 
изменять другие не предоставленные модули

## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
Полный объём локально гонять не нужно: клиента CRM в репозитории нет.
Оцените память процесса и число запросов к Postgres на указанных цифрах.
